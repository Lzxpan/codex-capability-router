# 1.0.1 release validation

This release adds Skill Preference Memory to the V1.0 routing contract. The release
preparation updates documentation and release checks; it does not introduce other
runtime features. Historical V1.0.0 / beta documents and visual assets are retained.

## Fresh checks after the final mutation

Declare `FINAL_MUTATION_COMPLETE = YES` after all code, tests, versions, references
and documentation are final. Then run from the repository root:

```bash
python -X utf8 -B -m unittest tests.test_preference_store tests.test_skill_preference_memory -v
python -X utf8 -B -m unittest discover -s tests -q
python -X utf8 -m compileall -q codex_capability_router tests scripts
python -X utf8 -B scripts/verify_release.py
git diff --check
```

The focused suite covers learning sources, metadata-only persistence, controller
exclusion, store management/failures, all three preference examples, user overrides,
deduplication, missing Skills, stale evidence, safe handoff and unchanged base batch
accounting. Full regression covers the existing Router contracts as well.

## Existing independent Host acceptance

The candidate acceptance used a temporary preference store, not the user's normal
store. Task A learned `substantial_project_work` → `work-log` through production
`update_preferences()`, with `learned_from=USER_MANUALLY_ADDED`, `enabled=true`
and only the six permitted preference fields.

Task B used a separate Host with `fork_turns=none` and the installed 1.0.1 candidate.
It first completed TaskAnalysis, discovery and normal Host batch decisions, then
froze base selection before its first preference load. Its base did not include
the remembered Skill. It loaded Task A's store, judged applicability, constructed
preference input and called the installed production `route()`.

The retained metadata evidence shows `work-log` added once with `MEMORY_ADDED`,
full handoff and a FINALIZED Receipt. Original batches retained 61 received and
61 semantically considered decisions, no unresolved candidates, and 5 base
selections; the final union contained 6 Skills. These are observations from that
acceptance task, not fixed inventory counts or new release-test inputs.

This is prior Host acceptance evidence, not a fresh independent Host run during
documentation release. Fresh library regression does not replace that experiment
or claim repeatable LLM outputs. No task prompts, source code, private paths or
full local inventory are committed as acceptance evidence.

## Boundaries and publication

The Host owns pattern semantics, first-read timing, user observations and actual
Skill execution. Python validates caller-supplied metadata; it neither generates
patterns nor chooses matching memory keys. Memory must not alter normal base
selection or original batch dispositions. An explicit prompt invoking the Router
cannot make it an eligible preference target.

Empty/disabled Memory preserves existing routing outputs. Strict external Receipt
consumers need to accept optional `preference_evidence` when enabled. Inventory
cache, existing freshness recovery, handoff safety and batch protocol remain in
scope of regression. `provider_selected_total` retains its known preparation-era
diagnostic inconsistency; the final Provider list remains authoritative.

Only after required gates pass: commit the explicit release scope, non-force push
main, create a new annotated `v1.0.1` tag, push it, and create a GitHub Stable
Release with `draft=false` and `prerelease=false`. Never move an existing tag or
publish to PyPI. Python 3.11 runtime absence is reported as permitted above.

Check outputs may be appended to local evidence and the GitHub Release without
rewriting finalized repository content. A hook freshness check supplements the
complete results; it does not replace them.
