# Codex Capability Router 1.0.1

Skill Preference Memory remembers which Skills a user tends to add for a type of
work, so the Host can supplement normal selection on a later similar task.

## 本版更新

- 新增 Skill 選用偏好：工作類型 → 使用者偏好的 Skill → 下次相似工作補選。
  `code-comments`、`humanizer-zh`、`work-log` 是例子，不是預植規則。
- Host LLM 從使用者明確指定或手動補選判斷可重用的習慣，也負責 task pattern
  與相似性判斷。Python 不做 semantic selection、keyword mapping 或次數門檻判斷。
- 正常 Host batch decisions 與 base selection 先凍結，再首次讀取 Memory。
  Memory 只補選，保留 `MODEL_SELECTED` 與原始 batch accounting。
- Receipt 的可選 `preference_evidence` 區分 `MODEL_SELECTED`、`USER_SPECIFIED`
  與 `MEMORY_ADDED`；後者代表依使用者偏好補入，不代表已執行成功。
- 學習 API 沿用 production eligibility，逐筆拒絕 controller／routing-support
  Skill，同一 payload 的合法偏好仍可更新。`MODEL_SELECTED` 不建立使用者偏好。
- Memory addition 仍通過 identity、eligibility、完整 handoff 與 freshness
  validation；本輪使用者明確指定／排除優先，已選到的 Skill 不重複加入。
- 本機 JSON 只保存六個允許欄位，提供查看、停用／啟用、單筆刪除與全部清除。
  不保存工作內容：raw prompt、source code、bug、solution、project details、
  private paths、credentials 與 hidden reasoning 都不屬於 Memory。

## 跨任務驗收與相容性

候選版已有獨立 Host 跨任務驗收：Task A 手動補選 `work-log`，透過 production
storage API 建立 `substantial_project_work` 關聯，來源為 `USER_MANUALLY_ADDED`。
Task B 使用實際 Installed 1.0.1，在正常 base selection 凍結後重新讀取臨時
store，自行判斷適用，再由 production `route()` 補入 `work-log`，來源為
`MEMORY_ADDED`，完成完整 handoff 與 FINALIZED Receipt。

此紀錄是發布前既有的 Host 驗收；本輪文件定稿後的 fresh tests 與檢查結果另附於
GitHub Release。本次不重新產生 V1.0 圖片，保留全部 V1.0.0 與 beta 歷史資料。

Memory 關閉或空白時維持原有 Receipt 與 fingerprint。啟用偏好證據時，嚴格拒絕
未知 Receipt 欄位的外部 consumer 需支援可選 `preference_evidence`。
Inventory cache、TaskAnalysis、Provider protocol 與原有 Coverage Check 預算不變。

## 限制

- 自動讀取與學習依賴 Host 接入；一次獨立驗收不代表所有 Host 環境都會自動觸發。
- `route()` 不讀寫偏好檔案；Host 負責先後順序、來源判斷與 metadata-only 學習。
  Pattern 是否含私人或專案語意仍需 Host 判斷，格式檢查無法單獨保證零洩漏。
- 保留既有 `provider_selected_total` diagnostic inconsistency；以最終
  `selected_count` 與 finalized Provider 清單判讀選取，不在本版修正。
- 沒有 cloud memory、跨裝置同步、完整工作內容記憶或 Python 語意分類。
- Python 3.11 的實際執行與語法相容檢查分開報告；未安裝 runtime 時不宣稱已執行。
