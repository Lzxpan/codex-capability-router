# v0.2 LLM TaskAnalysis + Supporting Capability Selection Design

版本：`v0.2.0-beta.1`
狀態：Pre-release design and implementation record

本文件記錄目前已實作並通過 Phase 1–5 驗證的 v0.2 public contract。它保留
beta.4 的 Skill selection、production `route()`、Receipt 與 lifecycle 原則，
不建立第二條 route、workflow engine 或 Provider execution subsystem。

## 1. Product Goal

Router 先由 Codex LLM 理解完整工作，再分成兩個獨立層次：

- Skill：工作應該怎麼做，提供方法、專業流程與工作準則。
- Supporting Provider：目前 Host 已可直接呼叫的執行能力。

Python 只做 discovery、normalization、cache、fingerprint、canonical ID、
availability/eligibility、privacy 與 final validation；不做語意分類或語意
Provider ranking。

## 2. Architecture Overview

```text
User Request
  -> LLM TaskAnalysis
  -> strict schema validation
  -> prepare_route_context()       # Skill-only, lazy boundary
  -> LLM Skill Selection
  -> full SKILL.md handoff/applicability
  -> LLM Execution Needs
      -> empty: Supporting path not_required
      -> non-empty: prepare_supporting_context()
           -> runtime declarations and hard eligibility
           -> deterministic Provider digests
           -> LLM Supporting request_detail or final_selection
  -> validated_decision_payloads
  -> production route()
  -> revalidation, Receipt, FINALIZED
```

只有 `route()` 能建立正式 Receipt 與 `FINALIZED` 結果。

## 3. LLM TaskAnalysis Contract

`TaskAnalysis` 是 immutable strict structured output，欄位固定為：

```json
{
  "task_summary": "...",
  "work_items": ["..."],
  "deliverables": ["..."],
  "constraints": ["..."],
  "quality_expectations": ["..."]
}
```

所有文字都有長度、型別、privacy 與 bounded validation；集合欄位在 Python
內部固定為 tuple。validated 後不可修改，輸出 mapping 只提供新的 list 副本。
這些欄位不是固定 taxonomy，內容由 LLM 依工作自然產生。

## 4. Skill Selection Flow

保留 beta.4 semantics：

- recall-first Candidate Retrieval
- canonical Skill IDs
- runtime availability authority
- controller 與 routing-support exclusion
- Basic/Enriched Profiles
- full `SKILL.md` handoff 與 Final Applicability Check
- expanded retrieval 最多一輪
- correction 最多一次
- `selected` 或 `no_matching_skill`
- no silent fallback

Python 只準備與驗證候選，不替 LLM 決定 Skill 是否適用。

## 5. Execution Needs Contract

Skill applicability 完成後，LLM 可產生零個或多個 Execution Needs：

```json
{
  "execution_needs": [
    {"need": "...", "reason": "..."}
  ]
}
```

每筆只有 `need` 與 `reason`，不含 Provider ID、score、priority、taxonomy、
category 或 task mapping。Python 只做 strict schema、bounded text 與 immutable
normalization，不解讀語意。

## 6. Supporting Provider Model

Supporting Provider 是 Host runtime 的 provider-level callable surface。第一版
只接受已完成 runtime evidence certification 的 exact instance：

- MCP：`node_repl`
- builtin provider-equivalent Tool：`functions.exec_command`

App、Plugin、其他 MCP instance、其他 builtin tool 都不是目前 formal production
scope。

## 7. Provider Runtime Eligibility

`ReadinessEvidenceCertificate` 記錄：

- canonical provider ID 與 kind
- Host exact identity/grouping
- callable tool IDs
- expected schema/declaration fingerprints
- provenance
- verification scope
- deterministic normalization rule

符合目前 certified evidence 時，`node_repl` 可 normalize 為
`present/available/authorized/connected/runtime_callable=true`；
`functions.exec_command` 可 normalize 為
`present/available/authorized=not_required/connection=not_required/runtime_callable=true`。

任何 identity、grouping、schema、exposure、fingerprint 或 provenance 不一致都
變成 unknown 並排除。不可用 package、CLI、Marketplace、config 或名稱猜 ready。

## 8. `prepare_route_context()`

此 API 是 read-only、stateless、deterministic、Skill-only。它只準備：

- validated TaskAnalysis reference/projection
- canonical Skill candidates
- Basic/Enriched Profiles
- Skill eligibility 與 runtime facts
- handoff references
- Skill fingerprints/provenance
- Skill metrics
- deterministic context fingerprint

它不掃 Provider、不讀 tool schema、不建立 Provider digest、不呼叫 LLM、不建
Receipt，也不 finalize Route。舊 `task_summary` 只能作
`TaskAnalysis.task_summary` compatibility projection；若不一致即 reject。

## 9. `prepare_supporting_context()`

只有 `execution_needs` 非空才可呼叫。它同樣是 read-only、stateless、deterministic
context preparation API，不呼叫 LLM、不執行 Provider endpoint、不建 Receipt，也
不保存 workflow/session state。

空 needs 時固定輸出：

- `run_state=not_run`
- discovery/readiness/digest/detail preparation 全部 not_run
- 所有 Provider counts 為 0

非空 needs 時才讀 Host declarations、套用 hard eligibility、建立 digest 與 detail
references。

## 10. Deterministic Provider Digest

Digest 只對 hard-eligible Provider 建立，包含 public provider description、canonical
callable tool IDs、tool descriptions、required inputs、明示 output/side-effect、
Host provenance 與 schema summary。可移除 JSON boilerplate 與格式噪音，但不得
產生 category、provides、best_for、priority、score 或 semantic applicability。

相同 Host metadata 必須得到相同 digest fingerprint；metadata 改變必須改變
fingerprint。

## 11. Supporting Detail Expansion

第一輪 LLM 只能二選一：

- `request_detail`：只引用 hard-eligible Provider 與 exact callable tool IDs，最多
  2 個 Provider、4 個 tool，最多一輪。
- `final_selection`：直接提交最終 Provider decision。

Detail expansion 只取得 request 指定的 bounded references，不展開整個 schema、不
執行 endpoint。第二輪必須是 `final_selection`，不得再次 request_detail 或建立
correction loop。Receipt 只保存 expanded Provider/tool IDs，不保存完整 schema。

## 12. Supporting Selection Status

Supporting status 只有三種：

- `not_required`：Execution Needs 為空。
- `selected`：Execution Needs 非空且至少選到一個 Provider；即使有 unmet needs
  仍為 `selected`。
- `no_matching_supporting_capability`：Execution Needs 非空且零 Provider；此時
  所有 needs 必須列入 unmet。

Skill `selection_status` 與 Supporting status 完全獨立；例如
`no_matching_skill + selected` 是合法結果。

## 13. Structured Output Validation

`validated_decision_payloads` 只保存 schema-valid public structured results：

- `task_analysis`
- `skill_selection`
- `execution_needs`
- non-empty needs 時的 `final_supporting_decision`

空 needs 不得帶 Supporting context 或 Provider decision。Python 驗證 schema、
canonical IDs、kind、duplicate、hard eligibility、unmet need origin、fingerprints
與 privacy；不驗證 Provider 語意是否適合工作。

## 14. Production `route()` / Finalization

既有 `route(SelectionRouteInput(...))` 是唯一正式入口。它會：

1. 驗證 immutable decision payload。
2. 重新準備並比對 Skill context fingerprint。
3. 非空 needs 時重新準備並比對 Supporting context。
4. 重新驗證 readiness、declaration/digest fingerprints 與 selected Provider。
5. 驗證 full handoff、applicability 與 final selection。
6. 建立官方 Receipt，將 lifecycle 設為 `FINALIZED`。

Stale context、stale evidence、stale digest、失去 hard eligibility 或 unresolved
`request_detail` 都 reject finalize，不猜替代 Provider、不 silent fallback。

## 15. Receipt v0.2

Receipt 最小擴充包含：

- TaskAnalysis
- selected Skills 與 Skill selection status
- Execution Needs
- Supporting status、selected Providers、unmet needs
- Skill/Supporting context fingerprints
- Provider digest fingerprints 與 readiness/provenance summary
- Skill/Supporting metrics
- detail expansion flag 與 bounded expanded IDs
- `selection_state=FINALIZED`

Receipt 不保存 raw user prompt、conversation transcript、private reasoning、完整
SKILL.md、完整 tool schema、credentials、private file contents 或 private absolute
paths。

## 16. Legacy Frontmatter Normalization

`explain-code` 採 bounded compatibility normalization：

- 保留既有 scalar/block format
- 支援 simple `allowed-tools` list
- 只映射有限 scalar metadata
- 唯一 nested exception 是 `metadata.source_frontmatter` 的一層安全 scalar leaves

`source_frontmatter` 只用於 compatibility parsing，不推導 availability、role、
priority、installed 或 selection。unknown nested metadata、deeper nesting、invalid
list/object、malformed syntax、duplicate critical key、sensitive metadata、unavailable、
controller 與 routing-support records 仍 reject。

## 17. Metrics / Observability

Skill metrics：available、candidate、selected、candidate reduction ratio；available
為 0 時 ratio 為 `null`。

Supporting metrics：`run_state`、discovered、hard-eligible、selected、digest total
size、detail expansion used。空 needs 時所有 Supporting preparation metrics 為
`not_run` 與零值。

## 18. Privacy / Trust Boundaries

Host declarations、runtime evidence 與 LLM structured output 都視為不可信輸入，先
通過 bounded schema、identity、provenance、fingerprint 與 privacy gates。Local
filesystem path 只作 discovery input，不進 public Receipt；Host runtime evidence
是 availability authority。沒有可證明 evidence 就是 unknown，而不是 ready。

## 19. Compatibility with beta.4

保留：canonical Skill IDs、recall-first retrieval、full handoff、Final Applicability
Check、production route、Automatic Selection Receipt、`OPEN` → `FINALIZED`、new work
→ new route、`selected`/`no_matching_skill`、no keyword-to-ID mapping、no legacy
selector、no silent fallback、Skill/Provider 分層，以及 beta.4 Receipt compatibility
contract。

v0.2 新增欄位以 `decision_contract_version=v0.2-selection-decision-v1` 表示；舊
beta.4 `contract_version` 保留作 compatibility identifier，不與 package version
混用。

## 20. Python Automated Test Plan

Python tests 不呼叫 Codex LLM，使用 synthetic structured outputs 驗證：

- TaskAnalysis、Execution Needs、normalization、immutability
- context/readiness/digest fingerprints
- lazy not-run path、detail protocol、statuses、Receipt/privacy/lifecycle
- explain-code positive/negative fixtures
- 12 routing scenarios、beta.4 與 Phase 1–4 regression

## 21. Codex Live Acceptance Plan

Codex 主模型以自然工作需求產生 TaskAnalysis、Skill selection、Execution Needs 與
Supporting final selection。正式結果必須由 production `route()` 產生，不保存 private
reasoning。Phase 5 A–E 均已通過；D 選取 `node_repl`，E 選取
`functions.exec_command`。Detail expansion 未在五個案例自然觸發。

## 22. Implementation Phases

已完成五個 bounded phases：

1. TaskAnalysis + legacy frontmatter correctness
2. Skill-side context + v0.2 route contract
3. Lazy Supporting context + certified readiness/digest
4. Supporting decision + finalization
5. Full deterministic verification + Codex Live Acceptance

Phase 0 runtime evidence probe 保留為 readiness certification gate。沒有足夠 Host
evidence 的 Provider kind 不進 formal scope。

## 23. Stop Conditions

遇到 schema/privacy/fingerprint regression、Host evidence 不足、stale revalidation
失敗、Provider scope 需要放寬、需要第二條 route、workflow/session state、semantic
Python selection、auto-install/auto-auth 或 endpoint health probe 時，停止並等待
架構決策；不得猜測或靜默降級。

## 24. Explicit Non-goals

本版本不包含 keyword mapping、固定 capability taxonomy、embedding/vector database、
external LLM API、Reviewer Agent、multi-agent voting、workflow engine、recommendation
engine、auto-install/auto-enable/OAuth、marketplace crawler、App production support、
Plugin production support、其他未 certification 的 MCP/builtin provider，以及任何
Provider endpoint readiness probe。
